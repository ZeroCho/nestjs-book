## 1. 공식 문서 읽는 법 — nodejs.org/api

### 1-1. 버전을 먼저 맞춘다

문서 왼쪽 위에 **버전 선택기**가 있습니다. 내가 쓰는 버전과 다르면 없는 API를 보고 있을 수 있어요.

```bash
node -v          # 내 노드 버전 확인 → 문서도 같은 버전으로
```

노드는 버전마다 API가 꽤 달라집니다. "분명 문서대로 했는데 안 돼요"의 8할이 이 문제입니다.

### 1-2. Stability(안정성) 지수를 본다

문서의 API마다 이런 딱지가 붙어 있습니다.

| 표시 | 의미 | 실무에서 |
|---|---|---|
| `Stability: 0 - Deprecated` | 폐기 예정 | 쓰지 마세요 |
| `Stability: 1 - Experimental` | 실험적 | 언제든 바뀔 수 있음. 학습·토이엔 OK, 상용 서비스엔 신중히 |
| `Stability: 2 - Stable` | 안정 | 마음 놓고 쓰세요 |

블로그 글에는 이 표시가 없습니다. **공식 문서를 봐야만 알 수 있는 정보**라, 이것 하나만으로도 문서를 볼 이유가 됩니다.

### 1-3. 문서 구조에 익숙해지기

각 모듈 페이지는 대체로 이 순서입니다.

1. **모듈 개요** — 뭐 하는 애인지, `require`/`import` 방법
2. **클래스 / 메서드 목록** — 여기가 본문
3. 각 메서드마다 **시그니처 → 매개변수 설명 → 반환값 → 예제**

메서드 시그니처 읽는 법:

```
fs.readFile(path[, options], callback)
             ↑        ↑         ↑
          필수     [대괄호]=선택   필수
```

**대괄호는 생략 가능**이라는 뜻입니다. 이거 하나만 알아도 문서 읽는 속도가 확 붙습니다.

### 1-4. 즐겨찾기 해둘 곳

| 주소 | 용도 |
|---|---|
| `nodejs.org/api` | 노드 내장 모듈 전부 |
| `expressjs.com/ko/4x/api.html` | 익스프레스 req·res·app 전체 목록 |
| `orm.drizzle.team/docs` | 드리즐 |
| `docs.nestjs.com` | 네스트 |
| `developer.mozilla.org` (MDN) | 자바스크립트 문법 자체 |

## 2. AI에게 묻는 법

AI는 잘 쓰면 24시간 대기하는 조교입니다. 그런데 **질문의 질이 답의 질을 그대로 결정**합니다.

### 2-1. 나쁜 질문 vs 좋은 질문

**❌ 나쁜 질문**

```
노드 fs 알려줘
```

→ 교과서 같은 일반론이 돌아옵니다. 검색이 더 빨라요.

**✅ 좋은 질문 — 4가지를 같이 준다**

```
[환경] Node.js 22, Express 4.19, Windows 11
[하려는 것] 업로드된 이미지를 uploads 폴더에 저장하려고 합니다
[내 코드]
const upload = multer({ dest: 'uploads/' });
app.post('/img', upload.single('img'), (req, res) => {
  res.json({ url: req.file.path });
});

[에러 전문]
TypeError: Cannot read properties of undefined (reading 'path')
    at /Users/me/app.js:12:35

[질문] req.file이 왜 undefined인가요? 폼 쪽 문제인지 미들웨어 순서 문제인지 모르겠습니다.
```

정리하면:

1. **환경** — 노드/패키지 버전, OS
2. **의도** — 뭘 하려는지 (에러만 주면 AI가 엉뚱한 방향으로 고칩니다)
3. **코드** — 관련 부분 전체. 잘라내지 말고
4. **에러 전문** — 첫 줄만 말고 스택 트레이스까지

### 2-2. 에러가 났을 때의 기본기

```
에러 메시지를 그대로 복사 → 붙여넣기
```

농담이 아니라 이게 제일 강력합니다. 에러 메시지를 **읽지도 않고** 검색창에 넣는 사람과, 읽고 나서 넣는 사람의 차이는 있지만, 안 넣는 사람과의 차이는 훨씬 큽니다.

### 2-3. AI 답변을 검증하는 습관

AI는 **자신 있게 틀립니다.** 특히 이런 경우:

- **버전이 다를 때** — 옛날 API를 알려주는 경우가 흔합니다 (`body-parser` 따로 설치하라거나, 삭제된 옵션을 쓰라거나)
- **존재하지 않는 패키지·메서드를 지어낼 때** — 그럴듯한 이름으로 만들어냅니다
- **최신 라이브러리** — 학습 데이터 이후에 나온 건 모릅니다

그래서 최소한의 검증 루틴:

1. AI가 알려준 **메서드 이름을 공식 문서에서 검색**해본다 → 없으면 지어낸 것
2. 패키지를 추천하면 **npm에서 최근 업데이트 날짜와 주간 다운로드 수**를 본다
3. 코드를 그대로 붙여넣기 전에 **한 줄씩 읽어본다**

> **원칙**: AI 답변은 **초안**이지 정답이 아닙니다. 최종 확인은 공식 문서.
> 이 습관 하나가 여러분을 "AI 없으면 아무것도 못 하는 사람"이 아니라
> "AI로 10배 빨라진 사람"으로 만듭니다.

### 2-4. 이 강의 이후에 특히 유용한 질문 패턴

```
이 코드가 왜 이렇게 동작하는지 한 줄씩 설명해줘. 나는 노드 입문자야.
```

```
이 코드의 문제점을 보안·성능·에러처리 관점에서 각각 지적해줘.
```

```
이걸 하는 방법이 3가지 있다면 각각의 장단점과, 실무에서 뭘 많이 쓰는지 알려줘.
```
