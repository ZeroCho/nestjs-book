7-1

익스프레스의 한계, 그리고 네스트

12분 · 개념 + 라이브 코딩

NodeBird 코드로 익스프레스의 구조적 약점을 보이고, 네스트가 그것을 어떻게 푸는지 본다.

7-1 · 문제

순서를 바꿔도 에러가 안 난다

// 이렇게 써야 하지만
router.post('/join', isNotLoggedIn, join);

// 순서를 바꿔도 문법 에러 없음 — 동작만 이상해진다
router.post('/join', join, isNotLoggedIn);

미들웨어의 순서·역할이 코드의 규칙이 아니라 머릿속 규칙. 혼자면 OK, 팀이면 사고의 근원.

7-1 · 해법

같은 로직, 구조가 다르다

Express
router.post(
  '/join',
  isNotLoggedIn,   // 순서 규칙
  join,
);
Nest
@UseGuards(NotLoggedInGuard)
@Post('join')
join(@Req() req: Request) {
  // 잘못 쓸 수가 없다
}

부탁(“순서 조심”)이 명찰(@UseGuards)로. 내부적으로 익스프레스를 쓰므로 배운 게 쌓인다.

라이브 코딩

네스트 프로젝트 첫걸음

  1. nest new로 프로젝트 생성
  2. 폴더 구조 투어 · 데코레이터 첫인상
  3. 컨트롤러 하나로 응답 확인
결과 → 네스트가 뜬다. “5-1에서 ‘익스프레스는 구조를 강제하지 않는다’ 했죠. 네스트는 정반대 철학.”
7-2

모듈과 가드

15분 · 라이브 코딩

컨트롤러·서비스·모듈 3형제 구조를 잡고, 5-4의 로그인 미들웨어를 가드로 재작성한다.

라이브 코딩

모듈 구조와 가드

  1. 모듈 추가 — 컨트롤러 · 서비스 · 모듈 3형제
  2. isLoggedIn/isNotLoggedIn을 가드로 재작성 (5-4 회수)
  3. @UseGuards로 라우트에 부착
결과 → “부탁하던 게 명찰이 된다 — 잘못 쓸 수가 없는 구조.”
7-3

미들웨어·환경변수·프로바이더

16분 · 라이브 코딩

기존 미들웨어를 연결하고 .env를 붙이며, 의존성 주입(DI)의 핵심을 잡는다.

라이브 코딩

미들웨어부터 DI까지

  1. 기존 미들웨어(morgan 등) 연결
  2. @nestjs/config로 .env (5-3 dotenv 회수) + 직접 미들웨어 작성
  3. 프로바이더/서비스 주입
결과 → “new를 우리가 안 하고 네스트가 대신 해주는 것 = DI. ‘갈아끼우기 쉬운 구조’. 내부 동작은 노트 N-7.”
7-4

생애 주기 한 방: 인터셉터·필터·파이프

18분 · 개념 + 라이브 코딩

요청 하나가 통과하는 관문들을 그림 한 장으로 정리하고 직접 만들어본다.

7-4 · 개념

요청 하나의 여행

이 그림 한 장이 네스트의 전부. 출력해서 모니터에 붙여두세요.

라이브 코딩

관문들을 직접 만든다

  1. 인터셉터 제작 → 생애 주기 순서 정리
  2. 예외 필터 (3-3 에러 미들웨어 회수)
  3. 매개변수 데코레이터 + 파이프 · class-validator
결과 → “body 검증 if문 도배가 선언 한 줄로.” DI 스캐너·게이트웨이·이벤트는 노트 N-7. 부품 조립은 다음 섹션.
